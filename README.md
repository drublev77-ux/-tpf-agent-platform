# TPF Agent Platform — пилот

Автономные ИИ‑агенты TPF Technology ведут заказ — сайт, веб‑приложение, Telegram‑бот или интернет‑магазин — от заявки клиента до сдачи. Люди подключаются только по эскалации. Архитектура описана в документе «TPF Agent Platform — архитектура»; это код её первого этапа.

## Как идёт заказ

```
Заявка → Аналитик (ТЗ + смета) → [клиент: смета] → [предоплата, если включена]
       → Архитектор → Разработчик → QA/Security → Стейджинг на Vercel
       → [клиент: приёмка] → Релиз на Vercel → Сдан
```

- **Решения клиента — только два:** смета и приёмка. Остальное агенты делают сами.
- **Ревьюер** — отдельная модель. Он проверяет ТЗ, архитектуру и код и возвращает работу автору с замечаниями.
- **Гейты QA:** все маршруты на месте; `next build` проходит; `npm audit` не находит high/critical; ревьюер подтверждает критерии приёмки из ТЗ.
- **Эскалации.** Провал проверок трижды подряд, исчерпанный бюджет токенов, заказ вне пилота или падающая задача ставят заказ на паузу. Инженер получает уведомление и продолжает заказ через `/admin/orders/{id}/resume`.
- **Цена считается кодом, а не моделью:** часы из сметы × `HOURLY_RATE`.
- **Журнал событий только дописывается** (защищено триггером в БД). Из него строятся статус для клиента и аудит.

## Структура

```
src/tpf/
  orchestrator/states.py    граф состояний заказа (чистая логика, без I/O)
  orchestrator/service.py   переходы в транзакции, журнал, артефакты, уведомления
  orchestrator/queue.py     очередь задач на Postgres (FOR UPDATE SKIP LOCKED + аренда)
  llm/gateway.py            Anthropic API, структурный вывод через tool, бюджеты токенов
  agents/                   analyst, architect, developer, qa, devops, reviewer
  tools/sandbox.py          изолированная сборка в Docker
  tools/template.py         фиксированный шаблон Next.js; агентам разрешены только app/, components/, lib/, public/
  tools/deploy.py           деплой на Vercel через REST API
  tools/github.py           (опционально) код заказа в отдельный приватный репозиторий
  api/main.py               FastAPI: приём заказов, решения клиента, поток событий, операторские действия
  worker.py                 воркер: берёт задачи и запускает агентов
```

## Оплата (Stripe, 50/50)

1. Клиент утверждает смету. Заказ ждёт предоплату: воркер создаёт ссылку Stripe Checkout на 50% и отправляет её клиенту.
2. Stripe сообщает об оплате вебхуком на `/webhooks/stripe`. API проверяет подпись, и агенты начинают работу.
3. Клиент принимает стейджинг. Заказ ждёт остаток: вторая ссылка на оставшиеся 50%.
4. После второй оплаты DevOps выкатывает сайт в production.

Суммы всегда берутся из утверждённой сметы и считаются кодом, а не моделью. Повторный вебхук не засчитывается дважды: в базе уникальный индекс. Если ссылка истекла (Stripe держит её 24 ч), клиенту автоматически уходит новая. Для оплаты по счёту укажите `PAYMENT_PROVIDER=manual`: оператор подтверждает оплату через `POST /admin/orders/{id}/payment`.

Как включить:

| Где | Переменные |
| --- | --- |
| Vercel (API) | `PAYMENT_PROVIDER=stripe`, `PREPAYMENT_SHARE=0.5`, `STRIPE_WEBHOOK_SECRET` |
| Railway (воркер) | `PAYMENT_PROVIDER=stripe`, `PREPAYMENT_SHARE=0.5`, `STRIPE_SECRET_KEY`, `PUBLIC_BASE_URL` |
| Stripe → Developers → Webhooks | endpoint `https://tpf-agent-platform.vercel.app/webhooks/stripe`, события `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.expired` |

## Кабинет клиента и письма

У каждого заказа есть личная страница `/portal/{id}?t=<токен>` (ru/en/zh, без JavaScript): статус, переписка,
ТЗ и смета, кнопки оплаты, ссылка на стейджинг, утверждение сметы и приёмка работы. Ссылку возвращает `POST /orders`
(`portal_url`), и она же стоит кнопкой в каждом письме.

Письма уходят через HTTPS API (Railway блокирует SMTP): `EMAIL_PROVIDER=resend|brevo`, `EMAIL_API_KEY`,
`EMAIL_FROM` (домен отправителя подтверждается у провайдера), `EMAIL_REPLY_TO`, `OPERATOR_EMAIL`.
Клиент получает подтверждение заявки, вопросы, смету, ссылки на оплату, стейджинг и сдачу — на своём языке.
Оператор — новые заказы и эскалации. Сбой почты заказ не останавливает.
Запасной провайдер: `EMAIL_FALLBACK_PROVIDER=resend|brevo`, `EMAIL_FALLBACK_API_KEY`, `EMAIL_FALLBACK_FROM` (пусто — как
`EMAIL_FROM`). Письмо, которое основной провайдер отказался принять, уходит через запасной; ошибка — только если отказали оба.

## Публичный сайт, консоль оператора, формы клиентских сайтов

- `/` — сайт TPF Technology (ru/en/zh); форма заявки создаёт заказ через `POST /orders` (не больше `INTAKE_HOURLY_LIMIT` в час).
  `/privacy` — политика обработки данных.
- `/admin` — консоль оператора. Вход по одноразовой ссылке на `OPERATOR_EMAIL`; список заказов, причина паузы, журнал,
  действия: снять с паузы, отметить оплату вне Stripe, добавить токены, отменить.
- Сданный заказ в кабинете клиента: «Скачать ZIP» с исходным кодом и доступ к приватному репозиторию по имени
  пользователя GitHub (нужны `GITHUB_TOKEN`, `GITHUB_OWNER`).
- Сайты клиентов могут содержать форму обратной связи — готовый компонент `tpf/ContactForm.tsx` из шаблона. Форма
  шлёт сообщение на `POST /forms/{order_id}`; платформа сохраняет его (`form_submissions`) и пересылает владельцу сайта.
- Тестовые версии собираются в отдельном проекте Vercel `tpf-order-N-preview`, рабочая — в `tpf-order-N`:
  окончательный адрес не занят, пока клиент не принял работу и не оплатил остаток.
- `VERCEL_TEAM_ID` принимает id команды (`team_…`) или её slug.

## Что платформа делает сама между заказами

- **Напоминает клиенту, который молчит.** Заказ ждёт ответов на вопросы, решения по смете или приёмки — через 2 и
  через 5 дней тишины клиент получает письмо‑напоминание (`CLIENT_REMINDER_DAYS=2,5`, пусто — выключено). Не чаще
  раза в сутки, не больше двух; заказ, простоявший больше 14 дней после последнего срока, не тревожим. Об оплате
  напоминаем только без Stripe: со Stripe клиент и так получает новую ссылку, когда прежняя истекла. Каждое
  напоминание записывается в журнал заказа (`client_reminder`) и видно клиенту в переписке. Код —
  `orchestrator/reminders.py`.
- **Сообщает поисковикам об изменённых страницах сайта** (IndexNow: Яндекс, Bing). Воркер отправляет адреса из
  `sitemap.xml` один раз на каждую версию сайта и только когда сайт уже отдаёт эту версию (`INDEXNOW=false` —
  выключить). Что и когда принято, лежит в `app_settings` (ключи `indexnow:…`). Код — `tools/indexnow.py`.
- **«Автоматизация процессов» как услуга.** Раздел на сайте и тип проекта в форме заявки. Это не отдельный тип
  продукта: Аналитик оформляет такой заказ как приложение (`app`) с возможностями `schedule`, `email`, `documents`,
  `ai`, `integrations` или как бота и сначала выясняет, что делается вручную и в каких сервисах.

## Что платформа строит

Тип заказа выбирает Аналитик (`product_type` в ТЗ). От него зависят шаблон проекта, правила для агентов, проверки и ставка
(`HOURLY_RATE_<ТИП>`, для заказов на русском — `HOURLY_RATE_RU_<ТИП>`).

| Тип | Что это | Что в проекте принадлежит платформе |
| --- | --- | --- |
| `site` | Статический сайт; единственная динамика — форма заявки | сборка, `tpf/ContactForm.tsx` |
| `app` | Веб‑приложение: база данных и админка владельца под `/admin`; ставится на экран телефона | `tpf/db.ts`, `tpf/auth.ts`, `tpf/notify.ts`, `/api/tpf-health`, манифест, иконки, service worker |
| `bot` | Telegram‑бот с базой и веб‑админкой | как у `app` без установки на телефон + `tpf/telegram.ts`, вебхук `/api/tpf-telegram` |
| `shop` | Интернет‑магазин: каталог, корзина, оформление, заказы, админка; ставится на экран телефона | как у `app` + `tpf/payments.ts`, вебхук `/api/tpf-stripe` |

Приложения, боты и магазины включаются переменной `TENANT_DATABASE_URL` на воркере. Это отдельный Postgres, где у каждого
заказа своя схема и своя роль: одна пара для версии на проверку, одна для рабочей.

### Интернет‑магазины

- **Деньги покупателей идут мимо платформы** — на собственный счёт владельца магазина у платёжного провайдера. Владелец
  выбирает провайдера и вводит ключи в кабинете заказа; платформа проверяет их у провайдера и кладёт в таблицу
  `tpf_secrets` в схеме магазина: магазин может её читать, но не менять.

  | Провайдер | Для кого | Что вводит владелец | Тест и работа |
  | --- | --- | --- | --- |
  | Stripe | продажи за рубеж | секретный ключ | `sk_test…` / `sk_live…` |
  | ЮKassa | бизнес в России, рубли | shopId и секретный ключ | ключ тестового магазина `test_…` / рабочего `live_…` |
  | bePaid | бизнес в Беларуси | ID магазина и секретный ключ | ключ один: на проверке платежи тестовые, после запуска настоящие |

- **Код магазина одинаков для всех провайдеров**: Разработчик пишет `createCheckout(...)` и `onPaid(...)`, а какой
  провайдер подключён, знает только `tpf/payments.ts` (исходник — `tools/shop_payments_ts.py`).
- **Настоящие деньги — только в запущенном магазине.** Версия на проверку работает в тестовом режиме: заказы в ней
  временные. Рабочий ключ Stripe или ЮKassa, введённый раньше, ждёт релиза.
- **Без ключей магазин работает**: принимает заказы без онлайн‑оплаты.
- **Заказ становится оплаченным только по слову самого провайдера.** Stripe подписывает события, и `/api/tpf-stripe`
  проверяет подпись. У ЮKassa и bePaid проверяемой подписи нет, поэтому их уведомлениям (`/api/tpf-pay`) магазин не
  верит: получив уведомление или встретив покупателя, вернувшегося со страницы оплаты (`/api/tpf-pay-return`), он сам
  спрашивает провайдера, прошёл ли платёж. Какой платёж относится к какому заказу, магазин записывает в `tpf_payments`.
  Дальше всё попадает в `onPaid` из `lib/payments.ts`: он сверяет сумму с заказом и срабатывает один раз.
- **ЮKassa: адрес уведомлений владелец добавляет сам** в кабинете ЮKassa (платформа показывает адрес в кабинете заказа):
  зарегистрировать его через API с ключом магазина нельзя. Без него оплата засчитывается, когда покупатель возвращается
  в магазин. Данные для чеков в ЮKassa магазин не передаёт.
- **Перед показом клиенту магазин сам доказывает, что умеет засчитывать оплату.** QA просит собранный магазин
  (`/api/tpf-check`, отвечает только по одноразовому токену и только в версии на проверку) создать временные заказы и
  провести по ним `onPaid`: оплата точной суммой должна отметить заказ оплаченным, повтор — ничего не менять, другая
  сумма или валюта — не засчитываться. Заказы после проверки удаляются, письма владельцу на это время отключены. Магазин,
  не прошедший проверку, возвращается Разработчику. Проверка появилась после того, как первый настоящий платёж в сданном
  магазине не засчитался: `onPaid` читал сумму из поля с выдуманным названием.
- **Сданный заказ можно выложить заново** (`POST /admin/orders/{id}/redeploy`): из последнего кода и текущих файлов
  платформы, без смены статуса и без писем клиенту.
- **Цены — целые числа в минимальных единицах валюты**, итог считает сервер по базе; из браузера приходят только
  идентификаторы товаров и количества.
- Клиентам, которым не подходит ни один из трёх провайдеров, магазин сдаётся с заказами без онлайн‑оплаты.

### Установка на телефон

Приложения и магазины — это PWA: у них есть манифест, иконки и service worker, поэтому их можно добавить на главный экран
телефона, и они открываются на весь экран со своей иконкой. Без сети показывается страница «нет соединения»; данные не
кэшируются. В магазины приложений (App Store, Google Play) они не публикуются.

## Боевое развёртывание: Vercel + Supabase + Railway

| Часть | Где | Как |
| --- | --- | --- |
| API | Vercel, проект `tpf-agent-platform`, регион fra1 | `app.py` + `vercel.json`, деплой из этого репозитория |
| База | Supabase, проект `tpf-agent-platform` (eu-central-1) | миграции из `src/tpf/migrations` (применяются вручную); приложение ходит под ролью `tpf_app` через пулер `:6543` |
| Воркер | Railway (или Fly.io/Render) | `Dockerfile.worker` + `railway.json`, `SANDBOX=vercel` |

Воркеру Docker не нужен: сборку и `npm audit` каждого сайта выполняет Vercel как превью‑деплой. Зелёное превью сразу становится стейджингом.

Переменные воркера: `DATABASE_URL` (та же строка, что у API), `ANTHROPIC_API_KEY`, `VERCEL_TOKEN`, `SANDBOX=vercel`, при желании `NOTIFIER=webhook` + `NOTIFY_WEBHOOK_URL`.

Бесплатный тариф Vercel (Hobby) по правилам Vercel предназначен только для некоммерческого использования. Перед работой с реальными клиентами переведите проект на Pro.

## Локальный запуск

```bash
cp .env.example .env        # задайте ANTHROPIC_API_KEY, VERCEL_TOKEN, ADMIN_TOKEN
docker compose up --build
```

API будет на `http://localhost:8000`, документация — на `/docs`.

```bash
# Клиент оставляет заявку
curl -X POST localhost:8000/orders -H 'content-type: application/json' -d '{
  "client_name": "Анна", "client_email": "anna@example.com", "language": "ru",
  "request_text": "Нужен лендинг для кофейни: меню, адрес, часы работы, кнопка звонка"}'
# → {"order": {...}, "client_token": "..."}

# Статус в реальном времени (SSE)
curl -N localhost:8000/orders/1/events -H 'X-Order-Token: <client_token>'

# Решения клиента
curl -X POST localhost:8000/orders/1/estimate   -H 'X-Order-Token: …' -H 'content-type: application/json' -d '{"approved": true}'
curl -X POST localhost:8000/orders/1/acceptance -H 'X-Order-Token: …' -H 'content-type: application/json' -d '{"approved": false, "comment": "Крупнее кнопку звонка"}'

# Оператор
curl localhost:8000/admin/orders?state=paused -H 'X-Admin-Token: …'
curl -X POST localhost:8000/admin/orders/1/resume -H 'X-Admin-Token: …' -H 'content-type: application/json' -d '{"note": "поправил конфиг"}'
```

Уведомления клиенту уходят на `NOTIFY_WEBHOOK_URL` (`NOTIFIER=webhook`). Оттуда их удобно разводить по e‑mail, Telegram, WhatsApp или WeChat, например через n8n.

## Тесты

```bash
pip install -e ".[dev]"
TEST_DATABASE_URL=postgresql://tpf:tpf@localhost:5432/tpf_test pytest
```

Тесты прогоняют заказ целиком на настоящем Postgres, с подменёнными моделью, песочницей и деплоем:

- путь от заявки до сдачи;
- вопросы клиенту;
- цикл «провал сборки → доработка → эскалация → продолжение»;
- отказ ревьюера и исправление;
- заказ вне пилота;
- исчерпание бюджета;
- правки клиента после стейджинга;
- отмена заказа;
- неизменяемость журнала;
- API.

## Что проверено, а что нет

- **Проверено:** 67 тестов проходят. Шаблон магазина реально собирается (`next build`, `npm audit` без уязвимостей), а собранный магазин прошёл стенд с подменой Stripe: оплата создаётся ключом владельца; подписанное событие отмечает заказ оплаченным; поддельная, просроченная и отсутствующая подпись получают отказ; несовпадение суммы не проходит; повторная доставка ничего не меняет; манифест, иконки и service worker отдаются.
- **Так же на стенде проверены ЮKassa и bePaid** (38 проверок): запрос на оплату с ключами владельца, возврат покупателя, уведомление, недоступность провайдера, чужая сумма и чужой заказ, тестовый платёж в запущенном магазине.
- **Проверено на настоящем Stripe (тестовый режим):** заказ в сданном магазине оплачен картой 4242…, вебхук с подписью принят, заказ стал оплаченным, остаток уменьшился.
- **Не проверено:** оплата у настоящих ЮKassa и bePaid — нужны тестовые ключи. Запросы к ЮKassa и bePaid написаны по их документации.
- **Проверено раньше:** шаблон сайта реально собирается (`next build`, Next.js 16) и проходит `npm audit` без high/critical. Next.js 15 гейт безопасности отклонил из‑за уязвимости в postcss, поэтому шаблон переведён на 16.
- **Не проверено в работе:** вызовы Anthropic API и Vercel API — они написаны по документации, но в тестах заменены заглушками. Docker‑песочница тоже не запускалась: в среде разработки не было Docker. Первый реальный заказ стоит провести под наблюдением.

Ограничения пилота:

- Песочнице нужен доступ к npm‑реестру. Ограничьте ей исходящий трафик белым списком на уровне сети хоста.
- Воркер получает Docker‑сокет, а это полный контроль над Docker хоста. Запускайте воркеры на отдельной сборочной машине.
- Бюджет проверяется перед каждым вызовом модели, поэтому фактический расход может превысить лимит на один вызов.
- Один заказ ведётся одной задачей за раз. Параллельная разработка страниц — этап 2 вместе с переходом на Temporal.
